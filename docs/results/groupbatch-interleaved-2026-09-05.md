## 変更内容と数学的根拠

同じ局所演算子を持つグループを最大16列ずつ交互に配置した。
値は独立したまま、因子の記述と局所処理をwarp内で共通化する。
さらに同じworkのグループを占有マスクの数値順に並べた。
同じ局所状態では、マスクの数値順と展開した状態語の辞書順が一致するため、
各タイルの読み書き先も昇順になり、入出力の局所性が改善する。

元の転送演算子をT、配列配置の置換をPとしたとき、更新は
`P (I_L ⊗ T) P^-1`であり、任意の入力係数で元と一致する。
[証明とメモリ計画](../research/groupbatch-interleaved.md)に、単射性、マスク順序、
atomic先の分離、scratchの上限を記した。近似や状態の同一視は使わない。

区間探索を入出力タスクの構築時へ移し、stride除算とGPU担当先の計算には
既存の厳密な整数計算法を移植した。入出力タスクは16 bytesに収めた。
バッチ設定の転送は実行と同じCUDAストリームで順序を保証する。

実行前の容量判定に残っていた二コピー分の要求も修正した。
実際の一コピーの配置に、計画・実行前の判定・割当てを統一した。
これにより、n=27の10 GiB設定で計画と実行前判定が食い違う問題を解消した。

## 検証

- 独立したCPUの前向き遷移と19,296ケース、171,732,960係数が一致。
  通常・blockedの全係数、法2と2つのCRT素数、両窓と個別セル、全列幅、scratch境界、
  graph 0/1/2、WRAP32、MATCHLUT、p=1の両実装を検査した。
- Compute Sanitizer memcheck：幅14の144ケース、38,698,128係数で0エラー。
- n=9本体の36実行設定・72個の既知CRT剰余値が一致。複数剰余のgraph寿命も含む。
- n=20は計画・実行とも18 MiBを受理し、17 MiBを実行前に拒否。18 MiBで2つの既知値が一致。
- 前回のCSRバッチ経路も624ケース、3,096,912係数で再照合した。
- n=27向けsm_103 cubinのコンパイルに成功。物理B300上では実行していない。

独立テストで一度見つかった大入力の再実行時の不一致は、テストのpageable H2Dコピーの
完了待ちが不足していたことによる。変更前の実装でも再現し、入力転送の完了を明示して
解消した。本体の演算不一致としては数えていない。

## n=27への適用範囲と限界

全状態分のCSRが不要なので、前回の512 MiB転送表上限に依存しない。
n=27、LOW=14、HIGH=13、scratch 10 GiBでは、複数列に入る状態数の割合は
上側95.8860%、下側98.8827%。実際のホスト計画でも199/206バッチと一致した。
これは状態数で重み付けした配置割合であり、実測時間の割合ではない。

2 MiBのVMM粒度を使う8 GPU計画では、scratch最大9.99957 GiB、
メタデータの最悪値637.630 MiB/GPU、DP段階の保守的peakは254.069 GiB/GPU。
B300ではその機械の空き容量とVMM粒度で再計画する必要がある。
NVLinkを含む複数GPU実行とn=27全体の速度は未測定。

Nsight Computeは借用ホストで`ERR_NVGPUCTRPERM`となった。
帯域飽和を測定できていないため、メモリ律速になったとは断定しない。
単純な配列転置は、入出力の悪化で全体が遅くなったため採用していない。

## 再現方法

```
ARCH=sm_86 MEMCHECK=1 scripts/test/groupbatch-interleaved.sh
python scripts/test/groupbatch-runtime.py <n9-binary> --logs /tmp/groupbatch-runtime
python scripts/test/groupbatch-scratch.py <n20-binary> --logs /tmp/groupbatch-scratch
python scripts/bench/bench_groupbatch.py --baseline <before> --candidate <after> --n 20 --expected 2308006916 --output /tmp/groupbatch-bench.json
GROUPBATCH=1 GRIDFP_GROUPBATCH_LANES=16 NGPU=8 scripts/run/b300x8-exact.sh 27
```

runnerのバックエンド選択の既定値は変更していない。今回の経路は`GROUPBATCH=1`で選ぶ。
`GRIDFP_GROUPBATCH_LANES=1`は交互配置を無効にするが、新しい添字計算や順序は残るため、
変更前全体との比較には保存した変更前の実行ファイルを使う。
