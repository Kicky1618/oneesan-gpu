# B300 x8 HBM32 solver

The current n=27 default exact source is
`src/cuda/b300/oneesan_cuda_gridfp_b300_hbm32_factorized_reverse2_row6crt20_batch.cu`.
A memory-oriented production candidate using CUDA virtual-memory sparse rank tables
and a true-packed row-6 initializer is available as
`src/cuda/b300/oneesan_cuda_gridfp_b300_hbm32_factorized_reverse2_row6crt20_vmm_batch.cu`.
A newer pre-ranked sparse-orbit candidate additionally replaces the memory-dominant
lower transfer window by a two-Count in-place orbit and precomputes the LOW-factor
transition ranks:
`src/cuda/b300/oneesan_cuda_gridfp_b300_hbm32_factorized_fullprerank_orbit_batch.cu`.
It stores the authoritative DP state as uint32 residues sharded across all GPUs and
runs all CRT primes in one process, reusing HBM allocation, LUTs, and the prepared
schedule.

The transition path currently combines:

- transition-closed occupancy groups
- authoritative HBM sharding over up to 8 GPUs
- rank/unrank I/O for fragmented groups and tiled interval I/O for long canonical runs
- precomputed group schedule
- double-D stream overlap
- opportunistic full-MateID cache
- main-to-main local rank deltas
- NR/NL drop-N rank delta
- known transition rank ranges instead of recomputing them with `clz/ffs`
- relaxed atomic load + CAS modular addition through `cuda::atomic_ref`
- LOW/HIGH frontier LUTs
- checkpointed multi-prime CRT batch execution

## Production build

CUDA 13.3 / B300:

```bash
N=27 ARCH=native ./scripts/build/b300-hbm32-batch.sh
```

For n=27 the build script defaults to:

- source: `src/cuda/b300/oneesan_cuda_gridfp_b300_hbm32_factorized_reverse2_row6crt20_batch.cu`
- `LOW_LUT_K=14`
- `HIGH_LUT_K=13`
- `TARGET_W=28`

The VMM candidate is opt-in until it has been timed on the actual B300 x8 host:

```bash
ROW6_VMM=1 N=27 ARCH=native ./scripts/build/b300-hbm32-batch.sh
ROW6_VMM=1 NGPU=8 ./scripts/run/b300x8-exact.sh 27
```

`ROW6_VMM=1` builds a distinct `oneesan_cuda_gridfp_b300_hbm32_vmm_batch_n27`
binary, links the CUDA driver API (`-lcuda`), and records that link and the same
row-6 exact coefficient certificate chain in build provenance.

The current stronger candidate is also opt-in:

```bash
ROW6_PRERANK=1 N=27 ARCH=native ./scripts/build/b300-hbm32-batch.sh
ROW6_PRERANK=1 NGPU=8 ./scripts/run/b300x8-exact.sh 27
```

`ROW6_PRERANK=1` builds
`oneesan_cuda_gridfp_b300_hbm32_vmm_prerank_batch_n27`. It keeps the VMM/true-packed
row-6 path, runs the upper window with reverse2, and runs the lower window in-place.
For the lower window, owner transitions and all LOW/center-local closure transitions
use packed precomputed LOW-factor source/destination ranks; only RR closures whose
matching endpoint lies in the HIGH factor use the generic rank path. The build is
covered by the same row-6 CRT20 exact coefficient provenance chain and links `-lcuda`.

Small-n regression builds still use `src/cuda/b300/oneesan_cuda_gridfp_b300_hbm32_fullmate_dropN_batch.cu`.

### Experimental row-7 Tensor endcap

The row-7 dense Tensor-Core endcap is available as an opt-in benchmark path;
it is **not admitted for exact CRT results yet**.  Build it with:

```bash
ROW7_TENSOR=1 N=27 ARCH=native ./scripts/build/b300-hbm32-batch.sh
```

`ROW7_TENSOR=1` selects
`oneesan_cuda_gridfp_b300_hbm32_factorized_reverse2_row7tensor_batch.cu`, links
cuBLAS, and sets the low/high split to `ceil(n/2)` / `floor(n/2)`.  Its build
provenance includes the 41-MiB exact compact row-7 table as an auxiliary
dependency, but the 600+ MiB extraction inputs and generator are still only in
`work/formal-probes`, so the table does not yet have the clean-clone
reproducible certificate chain required by `b300x8-exact.sh` and
`exact_safety.py`.  The exact wrapper therefore rejects `ROW7_TENSOR=1` before
probing GPUs or launching a solver.  Modular row-7 tables are cached under
`work/row7_mod_cache` by exact-table fingerprint and prime; override the cache
directory with `GRIDFP_ROW7_MOD_CACHE_DIR`.  Missing tables are built on the CPU
while the preceding CRT residue is executing on the GPU.

The row-7 initializer writes only the authoritative full-rank interval owned by
each GPU.  Prefix rows that cannot intersect that interval are removed before
the Tensor GEMM, avoiding eightfold duplication of the large `14|14` join on
B300 x8.  The `sm_100a` build was checked with CUDA 13.3; an actual 8x B300
benchmark is still required before making this path the default.

### Row-8 structural endcap and exact admission certificate

The row-8 source supports two initializer bases. The historical dense pivot/Hankel
path remains useful for modular benchmarking. The newer structural path uses a
930,824-byte modulus-independent sparse integer automaton (287,893 transition
nonzeros) and is admitted for exact CRT only when a deterministic width-specific
Grid-FP/structural integer-equality certificate is present. Build or benchmark the
dense path with:

```bash
ROW8_TENSOR=1 N=27 ARCH=native ./scripts/build/b300-hbm32-batch.sh
ROW8_TENSOR=1 NGPU=8 ./scripts/run/b300x8.sh 27 4294967291
```

`ROW8_TENSOR=1` selects
`oneesan_cuda_gridfp_b300_hbm32_factorized_reverse2_row8tensor_batch.cu`, links
cuBLAS/pthreads, and records `row8_pivots_w19.bin` in build provenance.  The
persistent certificate-sized input is only 45,536 bytes: the selected W=19
prefix/suffix words.  No pre-generated 72-MiB row-8 modular automaton is needed
by the production source closure.

For each previously unseen modulus the solver recomputes the W=9, W=10, W=19,
and W=20 cap-8 boundary coefficients on the GPU, constructs the nine basis
blocks and 25 dense one-symbol transition blocks, and writes a modular-table
cache under `work/row8_mod_cache`.  Override the directory with
`GRIDFP_ROW8_CACHE_DIR`.  A cache entry is about 71.3 MiB.  Its key/header binds
the modulus, pivot fingerprint, and a semantic builder ABI, while a payload hash
detects corruption.  A one-byte corruption test correctly rejected and rebuilt
the entry.  On the RTX 3070, an uncached production prime takes about 4.3--4.7 s
to construct; a warm cache removes this cost.

When several moduli and GPUs are available, `GRIDFP_ROW8_PREBUILD_CACHE` is
enabled by default for the multi-GPU row-8 path.  Independent moduli are assigned
to devices so their modular tables can be built in parallel before the residue
loop.  For a 20-prime n=27 run on eight GPUs this is at most three waves of table
construction, although the actual B300 x8 timing has not yet been measured.

The row-8 Tensor initializer uses the same authoritative full-rank sharding idea
as row 7 and also prunes prefix generation by propagating each shard's required
final prefix set backwards through the prefix levels.  A one-GPU emulation of
eight shards at n=21 reproduced the known `p=4294967291` residue `998035516`;
the slowest emulated shard initializer was about 0.92 s on the RTX 3070.  The
latest n=27/W=28 source compiles for `sm_100a` with valid build provenance.

The structural path is selected with `ROW8_STRUCTURAL=1`. Exact admission is
fail-closed: `ROW8_TENSOR=1` by itself is rejected, and
`ROW8_TENSOR=1 ROW8_STRUCTURAL=1` is accepted only when
`formal/certificates/row8_gridfp_structural_w<W>.json` verifies for the requested
width. The certificate compares every production Grid-FP row-8 coordinate with
the structural initializer for enough near-2^32 primes that the CRT product
exceeds an independently computed integer difference bound. Thus successful
modular comparisons imply equality over `Z`, not merely finite-field agreement.

Currently committed certificates cover W=10 (n=9, 3 comparison primes) and W=22
(n=21, 6 comparison primes). W=28/n=27 intentionally remains rejected until the
7-prime B300 x8 certificate is generated. Generate/resume it with:

```bash
NGPU=8 TARGET_MIB=16384 GRIDFP_VRAM_RESERVE_MIB=8192 \
  ./scripts/certify/row8-gridfp-structural.sh 27
```

The certification runner stores one immutable log per comparison prime under
`build/row8-gridfp-structural-w28/parts`. It binds resume state to the comparator
binary and build-provenance SHA-256, rejects modified partial logs, and can resume
after interruption without recomputing completed primes. Once every prime part is
present, certificate aggregation/reverification no longer requires a GPU. The
exact checkpoint/result format is V4 and binds the admission-certificate schema
and SHA-256, so changing the certificate invalidates resume and final-result
verification. Direct invocation of `solve_b300_exact_batch.py` cannot bypass this
gate: row-8 structural build provenance itself requires a verified admission
certificate and forces the structural runtime mode.

The runner has a pool of 48 distinct primes immediately below `2^32`, but only uses
the shortest prefix needed for a rigorous exact reconstruction. The current bound is much
tighter than the old edge-subset or raw cycle-space bound. Fix an outer-boundary s-t path
`P0`. Every s-t path is a T-join and is uniquely `P0 XOR boundary(F)` for a subset `F` of
the `n^2` bounded faces. At an interior vertex `P0` has degree zero; a checkerboard pattern
on the four surrounding face bits would select all four incident edges, which is impossible
for a simple path. Therefore the answer is bounded by the number of checkerboard-free
`n x n` face-bit matrices. The runner counts checkerboard-free strips of height at most 9
by an exact transfer matrix and partitions the rows into strips, deliberately ignoring
constraints between strips so the product remains a rigorous upper bound. For `n=27`,
the best current partition is `9+9+9`, with a 633-bit integer bound. Nineteen near-32-bit
primes provide only 608 bits, while 20 provide 640 bits, so exactly 20 primes are sufficient
under this bound. Every completed residue is written through the V3 crash-safe exact checkpoint format (binary SHA-256 binding, payload SHA-256, strict JSON validation, fsync + atomic rename) and the run resumes from the
first missing prime.

The GPU -> checkpoint -> CRT -> exact path was rechecked at n=4. Under the new bound, one 32-bit residue is already sufficient and reconstructs the CPU value `8512`.

## n=27 state and memory budget

Width 28 state counts:

- main: `385,719,506,620`
- blocked: `135,015,505,407`
- total uint32 authoritative state: about `1939.89 GiB`
- authoritative state per GPU on 8 GPUs: about `242.49 GiB`

The exact usable HBM is queried at runtime rather than inferred from the marketing
capacity. For reference, 288 GB decimal is about 274,658 MiB / 268.22 GiB. The
row-8 certification memory planner computes the worst authoritative shard, factor
tables, forced-window scratch, reserve, and an additional safety margin before any
comparison prime is launched:

```bash
python3 scripts/tools/row8_cert_memory_plan.py 28 --gpus 8 \
  --reserve-mib 8192 --safety-mib 1024
```

For W=28 the current plan is 248,305.803 MiB authoritative state per GPU,
304.280 MiB factor tables, and a maximum forced-window Count scratch of
15,124.540 MiB. Including the 8-GiB reserve and 1-GiB certification safety margin
gives a guarded minimum of 272,950.624 MiB/GPU. On a device reporting exactly
288 GB decimal this leaves only about 1.67 GiB, so the certification script rejects
undersized GPUs before launching the first prime. The production solver still uses
`cudaMemGetInfo` after LUT and authoritative allocations as the final runtime check.

The default dense factor-rank tables reserve 1024 MiB for LOW14 and 256 MiB
for HIGH13.  The VMM candidate keeps the same one-load device addressing but
reserves the full virtual address ranges and physically maps only pages containing
valid Motzkin words.  With the 2-MiB minimum VMM allocation granularity measured on
the RTX 3070 development host, the n=27 page counts are:

- LOW14: 1024 MiB virtual, 162 mapped pages = 324 MiB physical
- HIGH13: 256 MiB virtual, 44 mapped pages = 88 MiB physical
- complete factor GPU footprint including code/offset/base arrays: about 0.432 GiB

The runtime prints the actual VMM granularity and mapped page counts. `PLAN_ONLY`
queries device 0 automatically; `GRIDFP_VMM_GRAN_KIB` can override the granularity
for an offline target-machine estimate.

The host-side rank construction is sparse as well: it stores only `(code, packed
rank)` values and assembles one VMM page at a time.  For n=27, PLAN-process maximum
RSS fell from about 1,404,044 KiB with the old dense host rank arrays to about
171,456 KiB, while PLAN construction time stayed near 0.74 s.

The forced two-window schedule is:

### Window A

```text
p = 27..15
fixed lower occupancy bits = 14
groups = 16,384
LOW14 active
max Count scratch = 9.646 GiB
max Count+Mate scratch = 16.810 GiB
main-state volume eligible for 16-GiB Mate cache = 99.7507%
```

### Window B

```text
p = 14..1
fixed upper occupancy bits = 13
groups = 8,192
HIGH13 active
max Count scratch = 14.770 GiB
```

Window B uses the long-run interval I/O path, so the full MateID cache is not required
there. The scratch arena is capped by the effective target.

The VMM + true-packed-row6 candidate gives the following n=27 x8 PLAN values
when the VMM page granularity is 2 MiB:

```text
authoritative state / GPU     242.486 GiB
factor tables                   0.432 GiB
row-6 temporary                 1.259 GiB
row-6 peak                    244.177 GiB
maximum four-Count scratch     14.770 GiB
ordinary-DP peak              257.688 GiB
```

The old row-6 initializer used height-block arrays padded to 182 components at every
intermediate ternary word.  The true-packed initializer stores only the actual
height-block dimensions `141,182,135,68,25,6,1`; its row-6 temporary estimate falls
from about 5.05 GiB to 1.26 GiB.

The pre-ranked sparse-orbit candidate changes the ordinary-DP peak rather than the
row-6 peak. With a 2-MiB VMM granularity its n=27 x8 PLAN is:

```text
authoritative state / GPU     242.486 GiB
factor + VMM + pre-rank LUT     0.671 GiB
pre-rank LUT alone              244.62 MiB
row-6 temporary                   1.259 GiB
row-6 peak                      244.403 GiB
maximum Count scratch             9.646 GiB
actual scratch                    9.646 GiB
minimum ordinary-DP peak        250.687 GiB
actual ordinary-DP peak         250.687 GiB
```

This recovers about 4.89 GiB/GPU versus the VMM reverse2 path. On the RTX 3070,
`n=21, p=4294966997` measured `23.783 s / 14.006 s` wall/transition for reverse2
versus `20.815 s / 11.133 s` for the full pre-ranked orbit, while reproducing residue
`2124618149`. At n=20 the two paths are approximately tied. B300 x8 timing remains
the promotion gate before making this the default exact mode.

The scratch `TARGET_MIB` is a cap, not an amount eagerly allocated.  The forced
LOW/HIGH schedule is already maximally occupancy-partitioned.  At n=27 the largest
four-Count arena needs 15,125 MiB: 15,124 MiB does not fit, while every tested target
from 15,125 through 16,384 MiB gives the same `24574/24576` Mate-cache-eligible
groups and the same 14.770-GiB actual scratch peak.  Thus the previous
`authoritative + factor + 16 GiB` estimate was conservative; the current lifetime
model gives 257.688 GiB before the explicit driver/runtime reserve and other small
allocations.

## Why LOW14 / HIGH13

H100 n=23 experiments showed that making groups smaller was beneficial primarily
because the deeper frontier LUT removed more rank/unrank work, not because of HBM
bandwidth or group-launch overhead.

At the same 1-GiB scratch and identical 1024-group schedule:

```text
K4  : 335.967 s
K10 : 255.881 s
```

so deeper LUT specialization alone improved the run by about 23.8%.

A direct reduced-width asymmetric test compared one extra LOW bit against one extra
HIGH bit. Warm timings were close, with the deeper LOW side slightly ahead. Therefore
n=27 currently uses LOW14/HIGH13 rather than LOW13/HIGH14. The difference is small
enough that this choice should be rechecked on actual B300 hardware.

## Adaptive partition experiment

`src/cuda/b300/oneesan_cuda_gridfp_b300_hbm32_adaptive_lutbase_batch.cu` keeps an LUT-friendly base
partition and recursively splits only groups that exceed the memory target.

On RTX 3070, n=18 / 8 MiB:

```text

```

with identical residue. This remains a useful alternative when a uniform extra LUT bit

## Rank / atomic micro-optimizations

The current `opt` source adds two small improvements after the full-Mate/drop-N version:

1. Local main-to-main transitions pass their already-known changed rank interval directly,
   avoiding `src^dst` plus `clz/ffs` on every update.
2. Modular atomic addition uses `cuda::atomic_ref` relaxed load before the CAS loop,
   avoiding an initial read-via-`atomicCAS` RMW.

On an RTX 3070 n=17 reduced forced-two-window regression, the optimized source matched
all four tested prime residues and reduced warm runtime by roughly 3% versus the previous
forced-two-window source.

## Other atomic experiments

An exhaustive transition indegree probe through width 16 found at most 9 terms to a main
destination including identity, and at most 7 to blocked state. This allows raw uint32
`atomicAdd` when modulus is at most about 477 million.

A special `469762049 = 7*2^26+1` path was faster per residue, but exact-count throughput
was slightly worse because more small moduli are required. Production exact CRT therefore uses near-32-bit primes; with the current
checkerboard-strip bound, n=27 needs only the first 20 of the 48-prime pool.

## Row-6 CRT20 exact coefficient certificate

The n=27 production row-6 automaton no longer relies on an opaque generated coefficient table.
`formal/certificates/row6_rational_dump.txt.xz` contains the exact rational transition certificate
(558 basis states; 47,299 / 28,717 / 41,081 nonzero N/R/L coefficients).
`python3 scripts/tools/verify_row6_crt20.py` decompresses that certificate and checks every transition
destination and coefficient against `row6_automaton_mod1000000007.hpp`, then checks every one of the
20 CRT residue rows against the exact numerator/denominator. This covers 117,097 rational coefficients
under all 20 production primes. `scripts/tools/gen_row6_crt20.py` deterministically regenerates
`row6_automaton_crt20_generated.hpp`; the audited generated header SHA-256 is
`226e2299b755edf8d72efb8d724788a9d968f17432af65c367bea677ca7a822b`.

This certificate proves consistency of the generated CRT20 tables with the exact rational row-6
automaton. It is separate from the Lean proof of the path-count upper bound and from real-GPU kernel
execution validation.

## Exact result manifest

A completed exact run emits `exact_manifest.json` next to `checkpoint.json` and `exact.txt`. The
V3 manifest records every modulus/residue used in CRT, the checkerboard-strip bound and strip
partition, the solver identity, the exact checkpoint SHA-256, the `exact.txt` SHA-256, optional
build-provenance SHA-256, and a manifest SHA-256. New production builds emit
`ONEESAN_BUILD_PROVENANCE_V2`. V2 hashes the recursive CUDA/header include closure and also records
non-include generation inputs. For the n=27 row-6 CRT20 solver these auxiliary dependencies are the
compressed exact-rational certificate, its generator and verifier, and the shared path-bound/CRT-prime
source. `--verify-sources` checks all of them against the current checkout; ordinary checkpoint resume
still keys only on the solver binary SHA-256. Legacy V1 provenance remains accepted. Large integers
are stored as decimal strings so generic JSON consumers cannot round them.

```bash
./scripts/tools/verify_exact_result.py work/b300_exact_n27/exact_manifest.json \
  --binary build/oneesan_cuda_gridfp_b300_hbm32_batch_n27 \
  --verify-sources
```

The verifier deliberately does not import the runner's bound/CRT implementation. It recalculates
the checkerboard-strip bound using an independent XOR-based compatibility test, verifies every
listed modulus with deterministic Miller-Rabin for unsigned 64-bit integers, checks pairwise
coprimality and that the final modulus is not redundant, rebuilds CRT from every residue, checks
the rigorous upper bound and wall-time accounting, parses the V3 checkpoint semantically, and
hashes the checkpoint, `exact.txt`, and optional solver binary. Under `--verify-sources`, if a V2
source closure contains the row-6 CRT20 generated header, the verifier additionally requires the
canonical generator/verifier/path-bound/certificate auxiliary roles and reruns the exact-rational
certificate check before accepting the result.


### Group runtime constant batching (2026-08-27)

The full-pre-rank path originally issued many synchronous `cudaMemcpyToSymbol` calls for every forced group (DP tables, masks, widths, factor blocks, and factor mode).  On RTX 3070 / n=21, profiling split the old gather-side time into roughly 2.73 s of group setup and 2.84 s of actual gather I/O.

The production `ROW6_PRERANK=1` source now packs all group-dependent constant state into one `GroupRuntimeCfg` and uploads it with a single `cudaMemcpyToSymbol` per group.  The compact inverse-closure representation remains unchanged.  An alternating same-GPU A/B against the immediately preceding compact-inverse source gave 22.48--22.61 s vs 20.15--20.23 s wall time at n=21 (about 10.7% faster overall); absolute times remain clock/thermal dependent.  The n=20/n=21 known-residue regression and a second CRT prime still pass.

The n=27 / 8-GPU memory plan is unchanged by this optimization: 355 MiB/GPU pre-rank LUT, 0.779 GiB/GPU factor data, 7.385 GiB/GPU Count scratch, and about 250.650 GiB/GPU ordinary-DP peak with 2 MiB VMM granularity.

The same packed `GroupRuntimeCfg` upload and split main/block gather/scatter streams are now also used by the `OWNERFUSED=1` n=20..26 candidate. This matters because the first owner-fused prototype still paid the old per-group constant-upload path and default-stream synchronization overhead. On RTX 3070, n=21 / modulus `4294966997` / 1282 MiB scratch reproduced residue `2124618149` and measured 31.695 s for the current non-fused pre-rank owner-block path versus 27.126 s for owner-fused + packed group config in the first same-session A/B. Reversing the order gave 30.062 s versus 29.363 s. Clock variation is therefore material, but both orders favor the combined candidate and all compared residues match. A second n=20 prime reproduced residue `2308006916` modulo `4294967291`.

For n=26/W=27, `OWNERFUSED=1` still plans comfortably inside B300 HBM: about 84.915 GiB authoritative state per GPU, 0.454 GiB factor/pre-rank data, 2.562 GiB Count scratch, and about 87.930 GiB ordinary-DP peak per GPU on eight GPUs (assuming 2 MiB VMM granularity). Thus this optimization is throughput-oriented for n=26 rather than a memory-feasibility requirement.

### Block-ordered fused closure candidate (2026-08-29)

`BLOCKFUSED=1` selects
`src/cuda/b300/oneesan_cuda_gridfp_b300_hbm32_factorized_fullprerank_orbit_blockfused_batch.cu`.
This candidate combines the contiguous blocked-state owner traversal of the production
full-pre-rank path with the non-atomic fast-closure accumulation from the owner-fused
experiment.  For every `p>1` blocked destination, all same-factor closure predecessors
are pre-grouped by destination and accumulated by the unique blocked-state owner.  Only
closures that cross the LOW/HIGH factor boundary retain atomic updates; the `p=1`
main-to-main closure path remains on the independently validated inverse-closure code.

Build and run it explicitly with:

```bash
BLOCKFUSED=1 N=27 ARCH=native ./scripts/build/b300-hbm32-batch.sh
BLOCKFUSED=1 NGPU=8 ./scripts/run/b300x8-exact.sh 27
```

It is intentionally opt-in until an actual B300 x8 timing is available.  The ordinary
`OWNERFUSED=auto` policy is unchanged.

RTX 3070 correctness checks reproduced:

- n=20, p=4294967291: `2308006916`
- n=21, p=4294966997: `2124618149`
- n=21, p=4294967291: `998035516`

A same-clock n=21 / p=4294966997 comparison at 1282 MiB scratch measured the current
blocked-order production source at 18.3344 s wall / 10.9119 s transition and block-fused
at 17.8535 s wall / 10.4533 s transition.  This is about 2.6% wall and 4.2% transition
improvement on that run.  Earlier much larger apparent differences were traced to large
RTX 3070 clock/power-state variation and are not used as the performance claim.

The n=27 / 8-GPU / 2-MiB-VMM-granularity PLAN is:

```text
authoritative state / GPU     242.486 GiB
factor + pre-rank data          0.948 GiB
row-6 peak                    244.693 GiB
Count scratch                   7.385 GiB
ordinary-DP peak              250.819 GiB
```

The current production pre-rank plan is about 250.65 GiB/GPU, so closure fusion costs
roughly 0.17 GiB/GPU while remaining comfortably inside the B300 memory budget.

Two follow-up experiments were rejected.  Splitting fast closure into a separate sparse
kernel added another global pass and was unstable/slower once GPU clock state was
controlled.  Sharing `f_find_block` searches across a warp also regressed the controlled
n=21 run by about 1%, so the ordinary per-thread block lookup remains in the candidate.


### Interleaved GROUPBATCH update (2026-09-05)

`GROUPBATCH=1` now places up to 16 same-geometry groups in adjacent columns
(`GRIDFP_GROUPBATCH_LANES=1,2,4,8,16,32`). Equal-work groups are sorted by the actual
occupancy mask, which makes each tile row's global ranks monotone. Factor descriptors
are shared within the tile; values and cross-factor masks remain independent.
The implementation still uses one copy of the main and blocked scratch arrays.

The runtime's obsolete two-copy admission check has been replaced with the same
aligned one-copy calculation used by planning and allocation. In particular, the
n=27 10-GiB plan no longer encounters a contradictory two-copy rejection at runtime.
The n=20 regression accepts 18 MiB and rejects 17 MiB, checking both CRT residues.

See the [proof and memory analysis](research/groupbatch-interleaved.md) and the
[RTX 3090 measurements and validation](results/groupbatch-interleaved-2026-09-05.md).
These are single-GPU measurements; physical B300 x8 performance remains unmeasured.
The older measurements below describe the preceding implementations.

### Packed GROUPBATCH candidate (2026-08-30)

`GROUPBATCH=1` selects
`src/cuda/b300/oneesan_cuda_gridfp_b300_hbm32_factorized_fullprerank_orbit_blockfused_groupbatch_batch.cu`.
It keeps the block-ordered fused same-factor closure logic above, but packs many forced-occupancy
groups into one scratch arena and executes each `p` across the whole packed batch.  Owner and
cross-factor work are flattened into precomputed tasks, so the number of kernel launches and
per-group runtime setup operations is much smaller than in `BLOCKFUSED=1`.

The prepared batch descriptors are static across rows and residues.  Device task/config buffers are
uploaded lazily once per batch/GPU and then reused.  Transition launches use a CUDA Graph by default
(`GRIDFP_GROUPBATCH_GRAPH=1`); `0` disables it and `2` remains an experimental whole-pipeline graph.
A later n=20 1/2/1 comparison measured 4.990 s / 4.912 s / 4.797 s, so mode 2 did not show a
repeatable advantage and is not the default.
The task chunk defaults to 8192 elements for W<28 after RTX 3070 tuning, and to 65536 for W=28 to
bound n=27 metadata.  A build-time override is available with `GROUPBATCH_CHUNK=<elements>`.

The `p=1` inverse closure is destination-owned by default (`GRIDFP_GROUPBATCH_P1_DEST=1`).  The old
path grouped predecessors only within one source center block and then atomically added those partial
sums to the destination.  The new table merges all three source-center blocks by final destination;
one thread owns each `(high-row, height, destination-center, low-rank)` and reduces at most seven
predecessors with ordinary modular additions before one non-atomic store.  Set
`GRIDFP_GROUPBATCH_P1_DEST=0` to restore the old atomic path for comparison.  At n=21 the table has
17,302 destination records / 26,620 source entries (0.234 MiB); at n=27 it has 414,583 / 673,699
(5.733 MiB).  The n=27 10-GiB PLAN drops p=1 batch tasks from 816,271 to 743,698 and total resident
batch metadata from about 596.1 MiB/GPU to 594.4 MiB/GPU.  On n=20, six alternating RTX 3070 runs
put transition time at about 2.5825 s with destination ownership versus 2.5923 s on the atomic path
(roughly 0.38%); wall-time improvement is smaller and remains within the machine's clock/thermal
noise.  Two-prime n=20/n=21 correctness regression passes on the destination-owned path.

Build and run the n=27 B300 x8 candidate with:

```bash
GROUPBATCH=1 N=27 ARCH=native ./scripts/build/b300-hbm32-batch.sh
GROUPBATCH=1 NGPU=8 ./scripts/run/b300x8-exact.sh 27
```

For `GROUPBATCH=1` at n>=27 the run wrappers now default to `TARGET_MIB=10240`,
`GRIDFP_GROUPBATCH_GRAPH=1`, and `GRIDFP_GROUPBATCH_P1_DEST=1`.  An explicitly supplied
`TARGET_MIB` still wins.  The 10 GiB
default is intended for the first physical B300 run; it gives more HBM margin than the older
16 GiB scratch default without changing the total transition task count.  To request the larger
arena explicitly, use `TARGET_MIB=16384`.

For chunk experiments, for example:

```bash
GROUPBATCH=1 GROUPBATCH_CHUNK=32768 N=27 ARCH=native \
  ./scripts/build/b300-hbm32-batch.sh
```

RTX 3070 correctness regression currently reproduces all of the following:

- n=20, p=4294966997: `3704549185`
- n=20, p=4294967291: `2308006916`
- n=21, p=4294966997: `2124618149`
- n=21, p=4294967291: `998035516`

A two-residue n=21 run at a requested 2200 MiB scratch also completes both residues in one process.
This specifically tests the scratch lifetime fix described below.  The current official n=20 binary
measured 4.992 s wall at p=4294966997 in one RTX 3070 run; the current n=21 binary measured 15.054 s
at p=4294967291 with 2200 MiB scratch.  Absolute RTX 3070 timings vary strongly with clock, power,
and thermal state.  Earlier adjacent A/B runs of the first GROUPBATCH implementation against
BLOCKFUSED favored GROUPBATCH by about 11.7--13.4% wall time in both execution orders, which is the
more useful performance comparison.

Task-chunk tuning at n=20/n=21 found the useful range near 8--12 Ki elements per task.  n=20 favored
8192 clearly in the measured sequence (5.019 s at 8192, 5.177 s at 12288, 5.997 s at 16384).  n=21
also favored the 8--12 Ki range over 32--128 Ki; 128 Ki was materially slower.  W=28 deliberately
keeps the larger 65536 default because shrinking the chunk multiplies resident task metadata and the
n=27 memory margin is more important than extrapolating a small-GPU launch optimum.

The n=27 GROUPBATCH memory model differs from the preceding BLOCKFUSED plan.  A packed batch can use
nearly the full configured scratch target, so the old single-group `7.385 GiB` Count-scratch number
must not be used as the GROUPBATCH DP peak.  With eight GPUs, 16 GiB scratch target, 2 MiB VMM
mapping granularity, dynamic-affinity scheduling, and the default 65536 task chunk, the current PLAN
reports:

```text
authoritative state / GPU       242.486 GiB
factor + pre-rank data            0.955 GiB
row-6 temporary extra             1.259 GiB
row-6 peak, no task metadata    244.701 GiB
resident task metadata / GPU      0.582 GiB   (596.079 MiB conservative worst case)
row-6 peak incl. metadata       245.283 GiB
max packed batch arena           16.000 GiB
ordinary-DP peak                260.023 GiB
minimum DP peak                 251.408 GiB
```

The two windows contain 123 and 124 packed batches respectively (247 total) at the explicit
16 GiB scratch setting.  The conservative metadata bound assumes dynamic scheduling eventually
causes every GPU to touch every batch; the one-copy metadata size is 596.079 MiB per GPU.  On a
nominal 288 GB B300 this plan fits, but the margin is only about 8 GiB before any additional
driver/runtime effects, so this is no longer treated as a large memory margin.

The safer wrapper default, 10240 MiB, produces 405 batches and a `254.023 GiB/GPU` ordinary-DP
peak.  For comparison, 8192 MiB produces 505 batches and `252.020 GiB/GPU`, while 12288 MiB
produces 332 batches and `256.023 GiB/GPU`.  The total flattened owner/cross/I/O task counts are
unchanged by these arena sizes; only the number of packed batch boundaries changes.  This makes
10 GiB a useful first-run compromise until real B300 timing tells us whether the extra batch
boundaries are measurable.

A runtime lifetime bug was fixed together with this accounting.  Previously the packed scratch arena
was reserved before the direct row-6 initialization, making the 16 GiB arena overlap row-6 temporary
storage even though the PLAN treated those phases as disjoint; a 2200 MiB n=21 run could therefore
fail during row-6 initialization.  The arena is now released before every residue's row-6 phase and
reserved only after row-6 temporaries have been freed.  If the arena address changes between CRT
residues, cached CUDA Graph executables are invalidated and recaptured because they contain the arena
pointer; task/config metadata remains resident and reusable.  PLAN includes that persistent metadata
in the row-6 peak for the multi-residue worst case.

Multi-GPU GROUPBATCH defaults to dynamic-affinity batch scheduling.  Batches have a preferred GPU
from a greedy work estimate, while idle GPUs may steal unclaimed batches.  This avoids permanently
binding an unlucky set of occupancy groups to one GPU while retaining locality when the preferred
assignment is balanced.  The n=27 PLAN shows affinity max/average work ratios of about 1.04 and 1.03
for the two windows.

GROUPBATCH remains opt-in until it has been timed and exact-validated on a physical B300 x8 system.
The corrected n=27 PLAN and local regression establish memory/correctness admission, not B300 runtime.
