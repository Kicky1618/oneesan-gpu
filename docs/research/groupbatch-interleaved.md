# 全状態の転送表を使わない、同型グループの交互配置

2026-09-05。対象は
`oneesan_cuda_gridfp_b300_hbm32_factorized_fullprerank_orbit_blockfused_groupbatch_batch.cu`。
既存の半幅pre-rank表と、その場更新を使うgroupbatchバックエンドを改良した。
CSR版の[一括転送](frontier-batch-and-rank.md)とは別の実装である。

## 状態を保存したまま配列の配置を変える

ウィンドウ内の非活動位置の占有マスクを固定すると、遷移はグループ外へ出ない。
同じ占有数を持つマスクについては、Nを取り除いた記号列と活動位置を保つ全単射があり、
局所順位、接続先、遷移の多重度を保存する。
半幅pre-rank表の適用時にも、通常・blockedの各FBlockの大きさ、stride、境界高さ、
中央記号が一致する。実装はこれらの一致をホスト側で検査してからまとめる。

L個の同型グループに、通常状態数m、blocked状態数dがあるとする。
グループg、局所状態iの通常配列アドレスを

```
P_main(g,i) = main_base + L*i + g,  0 <= g < L, 0 <= i < m
P_block(g,i) = block_base + L*i + g, 0 <= g < L, 0 <= i < d
```

とする。Lは1,2,4,8,16,32のいずれかで、既定上限は16。
P(g,i)=P(h,j)なら、Lを法としてg=h、従ってi=jである。
通常・blocked領域と別のタイルは分離して確保するため、全配置は単射になる。

既存カーネルの全ての読み書きとatomic先を、この写像で置換する。
各列では元のowner更新、局所closure、窓をまたぐ接続探索、p=1の処理がそのまま実行される。
隣接レーンの値は別のグループに属し、加算も同一視もしない。
跨窓接続の探索とグローバル入出力では、各レーン固有の占有マスクを使用する。
共通化するのは、等しいことを検査した因子の記述だけである。

元の局所演算子をT、配置の置換をPとすれば、実装した演算子は
`P (I_L ⊗ T) P^-1`。単なる状態番号の変更であり、任意の入力係数で同じ結果を与える。
これは既存の直和構造を利用した実装上の最適化で、一般の接続状態数を減らす新定理とは
主張しない。

ownerカーネルの更新先が重ならないこと、closureのatomic加算、カーネル間の順序は
既存方式から保存される。異なるレーンのatomic先も上の単射性から交わらない。
次の窓への移行時には従来どおりGPU workerを同期する。

## 全ての局所状態でグローバル番号を昇順にする

同じ占有数の二つのマスクA<Bを考える。各FBlock内の同じ局所番号は、両者で同じ
「Nを除いたR/L列」と、同じ活動領域の記号列に対応する。
AとBが異なる最上位の位置をqとすると、qより上の占有位置は一致するため、
そこに置かれるR/L記号も一致する。qではAがN、BがRまたはLになる。
記号の順序はN<R<Lなので、展開した状態語はA側の方が辞書順で小さい。
グローバルrankはこの辞書順の順位であり、従って **G_A(i)<G_B(i)**。
blocked側の窓に伴う一定の位置シフトでも、この順序は保存される。

この性質は全ての局所番号iで同時に成立する。そこでwork降順の中で、同じworkの
グループを占有マスク`mo`の数値昇順に並べ、隣接グループからタイルを作る。
各タイルの一行で読む・書くグローバル番号もレーン順に昇順になる。
グループの列を置換するだけなので、上の共役による正しさの証明は変わらない。
実際のキャッシュライン数や速度の最適性まではこの証明から主張しない。

列挙番号`g`は固定位置の上位ビットから順に割り当てられており、`mo`とはビットの
順番が逆になる。したがって列挙番号をそのまま局所性の指標にはしない。
GPU上での追加のソートや全状態の番号表は不要で、既存のホスト側sortの比較だけを変更する。

## 追加の大きな値配列を持たない

通常・blockedとも一コピーであり、Lグループの値は`4L(m+d)` bytesで収まる。
端数グループはLを小さくして別のタイルにするため、架空の列のパディングは不要。
実行前に必要量を二コピーとして計算する古い判定が残っており、計画との不一致もあった。
これを修正し、計画、実行前の判定、バッチ割当てで同じ一コピーの整列計算を使う。
n=27の最大グループは約7.385 GiBなので、従来の二コピー判定は10 GiB設定を不必要に
拒否していた。n=20では計画・実行とも18 MiBを受理し、17 MiBを拒否する回帰試験を設けた。

64要素単位の整列について、`align(L*m) <= L*align(m)`なので、交互配置後の
scratch使用量は従来のグループ別配置以下になる。

入出力タスクはFBlock境界で分割する。従来の各状態での区間探索を不要にし、
`i / stride`にはホストで準備した整数逆数と一回の補正を使う。
厳密性は`src/common/invariant_division.hpp`に記した。
GPU間の担当先は`src/common/shard_address.hpp`の最大3回の比較で求める。
いずれも近似除算ではない。

入出力タスクはcfg番号32ビット、sectorとFBlock番号を各16ビット、区間先頭64ビットの
16 bytesとする。sectorは0/1、FBlock番号は64未満なので狭めても情報を失わない。
n=27の両窓の15,913,336タスクについて、試作時の24 bytes形式より121.408 MiB小さい。
この管理情報とpre-rank表のメモリは、値配列とは別に計画へ含める。

タスクは先頭グループの記述を読み、threadの下位log2(L)ビットを列番号とする。
処理する論理区間は`GROUPBATCH_CHUNK/L`、threadの論理歩幅は`blockDim/L`。
サポートするthread数は64以上で、Lは最大32のため、歩幅は常に正である。

## graphと転送の順序

バッチのメタデータはscheduleと同じ寿命を持ち、CUDA graphに参照させる。
デバイスへ送る際は、gather・遷移・scatterと同じ非同期ストリームへコピーを並べる。
従ってpageableなホストメモリからのコピーがホストへ早く戻っても、カーネルが
未転送の内容を読むことはない。scheduleの再構築前には既存のgraphとデバイスメタデータを
破棄するという呼び出し側の規約を維持する。

独立テストでは、最初に入力する値配列のコピーも明示的に完了させる。
この待機がない初期テストは、変更前のバックエンドでも大きい入力の二回目に不一致となった。
[NVIDIAの同期仕様](https://docs.nvidia.com/cuda/cuda-runtime-api/api-sync-behavior.html)は、
pageableなホストメモリからの同期版cudaMemcpyでも、DMA完了前に戻る場合があると定める。
nonblockingストリームの実行を、メタデータ確保時の偶発的な同期に依存させてはいけない。

## n=27への適用範囲

`scripts/tools/groupbatch_layout_plan.py`は、正確な状態数、占有マスクの二項係数、
既存のwork順の並べ替え、scratch内への貪欲な割当てを整数で再現する。
全通常・blocked状態の合計520,735,012,027との一致も検査する。
n=27、LOW=14、HIGH=13、scratch 10 GiB、最大16列では、複数列に入る状態数の割合は
上側95.8860%、下側98.8827%。バッチ数はそれぞれ199、206となる。
これは状態数で重み付けした配置割合であり、時間短縮率ではない。
実際の`GRIDFP_PLAN_ONLY`でも199/206バッチと一致した。RTX 3090上で取得した2 MiBの
VMM粒度を使う計画では、8 GPUの一台あたりauthoritative配列242.486 GiB、
scratch最大9.99957 GiB、メタデータの最悪値637.630 MiBとなる。
DP段階の保守的なpeakは254.069 GiB/GPU。B300の実際のVMM粒度・空き領域は
その機械上で再計画する必要がある。

この方式はCSRの全状態分の列番号・行番号を作らないため、既定512 MiBの転送表上限や
32-bit scanの入場条件に依存しない。一方、全状態のauthoritative配列が巨大であることは
変わらず、n=27全体の実行には大容量の複数GPUが必要になる。
RTX 3090での小規模の速度比をB300のn=27へ外挿することはできない。

## 再現

```
ARCH=sm_86 MEMCHECK=1 scripts/test/groupbatch-interleaved.sh
python scripts/tools/groupbatch_layout_plan.py --n 27 --scratch-mib 10240 --lanes 16
GROUPBATCH=1 GRIDFP_GROUPBATCH_LANES=16 NGPU=8 scripts/run/b300x8-exact.sh 27
```

`GRIDFP_GROUPBATCH_LANES=1`は新しい添字計算を使う一列配置。
変更前全体との性能比較には、変更前の実行ファイルを保存して
`scripts/bench/bench_groupbatch.py --baseline ... --candidate ... --n ... --output ...`
を使う。runnerのバックエンド選択の既定値はこの変更では切り替えていない。
